# AGENTS.md

The single source of truth for coding agents (Claude Code, Codex, Cursor, and others) in this
repo. `CLAUDE.md` only imports this file. People should read `README.md` for commands and
`docs/HANDOFF.md` for project status and history.

## What this is

InvokeDB (code name "horizon"): a web app for building data tables you can query through an
API. A monorepo of two packages with **separate `node_modules`** (no npm workspaces):

| Package               | Stack                                                                      | Dev URL                 |
| --------------------- | -------------------------------------------------------------------------- | ----------------------- |
| `packages/horizon-be` | NestJS 12, TypeORM 1.x (Postgres), native `mongodb` 7 driver, `ws` 8       | :8001 (websocket :9000) |
| `packages/horizon-fe` | Vue 3, Vite 6, ag-grid 36, Element Plus. Public site at `/`, app at `/app` | :8000                   |

`deploy/` (see `deploy/README.md`) is the production setup: one server, `docker compose`,
driven from the Mac by `deploy/deploy.sh`. Its `prod.env` is a gitignored secret file.
`docs/OPERATIONS.md` is the entry point for operations: every outside service (Mailgun,
Telegram, UptimeRobot, Healthchecks.io, Cloudflare, DigitalOcean) and GitHub workflow, its
secrets (by name), who it alerts and how to check it.

`examples/` (see `examples/README.md`) holds the `invokedb` npm client (`invokedb-node`,
TypeScript + `fetch`, built with `tsc`), an Angular 22 example app (`angular`, imports the client
source via a tsconfig path), made-up CSVs (`data/`, regenerated by `data/generate.mjs`) and
`setup.mjs`, which loads them as tables into a running backend (`--base` for another port) and
writes `angular/public/invokedb.config.json` (gitignored, holds the API key). The client and the
Angular app each have their own `node_modules` and 2-space prettier style, so they're in
`.prettierignore`. The Angular CLI needs Node 22.22.3+ /
24.15+ (`.nvmrc` 22 works). Don't `npm publish` the client unless asked.
`examples/invokedb-python` is the Python client (#218: stdlib `urllib`, typed, Python 3.9+, not on
PyPI; don't publish unless asked). Its tests are `python3 -m unittest discover -s tests` in that
folder: offline against a stub server, plus live ones against a backend when `INVOKEDB_TEST_BASE`
is set (they make and delete their own table and key).

Logins (local and demo data): `demo@invokedb.com` … `demo7@invokedb.com`, password `password`.

## Commands

Run from the repo root. Every script loads `.env` through `scripts/env.sh`.

```sh
npm install                  # root tools, then both packages (postinstall: scripts/install-packages.sh)
npm run dev                  # backend + frontend (concurrently); Ctrl-C stops both
npm run db:setup             # create missing DBs + run pending migrations (safe)
npm run migration:create -- Name
npm run migration:run | migration:revert
npm run onboarding:funnel -- [--days 30] [--json]  # signup → first API call funnel (read-only)
npm run changelog            # rebuild the site's /changelog from merged `enhancement` PRs (needs gh)
npm run format               # prettier --write . (root prettier 3)
npm run format:check
npm run check                # what CI runs, minus the smoke test (scripts/check.sh)
npm --prefix packages/horizon-be run build   # tsc: the main backend correctness check
npm --prefix packages/horizon-be run lint    # ESLint (eslint.config.mjs)
npm --prefix packages/horizon-be test        # Jest unit tests (src/**/*.spec.ts)
npm --prefix packages/horizon-fe run typecheck  # tsc --noEmit over the frontend's .js (checkJs)
node scripts/api-smoke.mjs [base_url] [out.json]  # ~30 API calls against a running backend
node scripts/ui-smoke.mjs [--out out.json] [--headed]  # Playwright UI flows (load env first, see verify-frontend)
bash scripts/smoke-env.sh <file>  # throwaway env (horizon_smoke DBs, ports 81xx/9100) for both smoke tests
```

CI (`.github/workflows/ci.yml`) runs on every push to a PR and every push to `main` (a branch with
no PR gets no CI until one is opened; a dispatched CI run doesn't count toward a PR's required
checks, #40, #42): backend build + lint + unit tests, the API smoke test (`smoke` job: the built
backend on Postgres and Mongo service containers, then the Python client's live tests against
it), frontend build + lint + typecheck, the `examples/` builds, the Python client's offline
tests (`python-client`, #257), shellcheck (`deploy/*.sh`, `scripts/*.sh`; settings in `.shellcheckrc`) and
prettier; `npm run check` runs all but the smoke test locally. Dependabot
(`.github/dependabot.yml`) opens weekly update PRs. Unit tests are few so far (account scoping, validators, column-name rules); add a `*.spec.ts` next to the code
for new pure logic. Verify backend changes with `build`, `test`, and `api-smoke.mjs` (see the
`verify-backend` skill); if you can't run the smoke test locally, the `smoke` job runs it on the PR.
`api-smoke.mjs` exits non-zero on any failed call or check. Verify UI changes with `npm --prefix
packages/horizon-fe run build`, `run lint` and `run typecheck` (`checkJs` over `src/**/*.js`; files
marked `// @ts-nocheck` aren't checked yet, so drop the marker when you fix one; `.vue` files aren't
checked); don't drive a browser (Playwright MCP or otherwise) to check them unless the user asks.
The Playwright UI smoke test (`ui-smoke.mjs`, see the `verify-frontend` skill) is slow to set up, so
**only run it when the user asks**. `.github/workflows/e2e.yml` runs the same script against production
nightly and after each deploy, as a test account (#90; `docs/OPERATIONS.md`). Both smoke tests run against a throwaway stack, never the user's
data.

## Hard rules

- **The GitHub repo is public.** Never commit secrets, keys, tokens, customer data or real
  connection strings. Secret files (`.env`, `deploy/prod.env`, SSH keys) are gitignored, and
  their originals live in a Dropbox folder that `scripts/secrets.sh` syncs. Never add a secret
  file to git, never weaken `.gitignore`, and never push `~/dev/invokedb-pre-scrub-*.bundle`.
- **Pushing to `main` deploys to production** (after CI passes; `.github/workflows/cd.yml`).
  Never push or merge code to `main` yourself unless the user asks; `automerge.yml` merges PRs
  that qualify (below). Docs-only changes are the exception (below).
- **`deploy/deploy.sh` touches the real production server.** Run its server commands (`up`,
  `bootstrap`, `init-db`, `migrate`, `compose`) only when the user asks.
- **Destructive DB commands need the user's OK first:** `db:reset`, `db:demo`,
  `migration:revert`, and any `DROP` / `dropDatabase`. They only touch `horizon*` databases, but
  that is still the user's local data. For experiments, use throwaway DBs through
  `HORIZON_ENV_FILE` (see `verify-backend`).
- **No native (C/C++) npm packages.** The Xcode command-line tools on this Mac are broken, so
  anything with `node-gyp` fails to install. Install the backend with `--omit=optional`.
- Don't commit or push unless asked. Branch first if on `main`. Exception: when the user asks
  you to work an issue, committing, pushing its branch and opening its PR are part of the job
  (see "How work is tracked"); merging is left to `automerge.yml` or the user. Docs-only
  changes are committed and pushed straight to `main` when done (below).
- **Changes reach `main` through pull requests.** Push the branch, `gh pr create`; CI and the
  Claude review (`.github/workflows/review.yml`) run on it. Merge (`gh pr merge --merge`) only
  when the user says so. `main` has a rule requiring a PR with CI passing; never bypass it,
  except for docs-only changes.
- **Docs-only changes go straight to `main`, never through a PR.** If every file you changed is
  Markdown (`*.md`: `docs/`, `AGENTS.md`, READMEs, skills), commit on `main` and
  `git push origin main` (no issue, no branch, no PR). The ruleset lets the owner's login bypass
  the PR rule, and a Markdown-only push runs no CI and so doesn't deploy (#51). Run prettier on
  the files first, and `git pull --rebase` if the push is rejected. If a change mixes docs and
  anything else, it's not docs-only: use a PR. The cloud agent can't bypass the rule, so in
  GitHub Actions docs changes still go in its PR.
- **Auto-merge** (`.github/workflows/automerge.yml`): a PR into `main` merges, and so deploys,
  by itself once CI passes and the review labels it `review-ok`, unless it has the `hold` label
  or touches a held path (`deploy/`, `.github/`, migrations, `*.env.example`). Those get
  `needs-owner` and
  wait for the user. Add `hold` only when a PR can't deploy safely without the user: it needs
  a `prod.env` change or a manual step on the server. Never for a change that's large,
  risky-looking or visual (those merge by themselves), or for a follow-up the author can't do
  (list it under "Follow-ups" and open an issue).
- `.github/workflows/repair.yml` fixes failed CI or CD, or opens an issue. On an open agent PR's
  branch it pushes the fix straight onto that branch and comments on the PR (#135: a fix PR
  merged into the branch with the workflow token started no CI); anywhere else it opens a fix PR
  (`claude/fix-*`), and so after 2 direct pushes to a PR, or once it is `agent-stuck`, so a failing
  fix can't loop. `automerge.yml` merges those into feature branches after CI passes and the
  review labels them `review-ok`; its fix PRs into `main` follow the auto-merge rule.
- The site's `/changelog` (#219) is rebuilt before every deploy: `cd.yml` runs
  `scripts/changelog.mjs` and publishes the file as the `changelog` release's asset, and the
  web image's build fetches it (`deploy/web.Dockerfile`), keeping the repo's copy if it can't
  (#259). A removed feature's PR goes in the script's `SKIP`.
- Give the user one step at a time: only the next thing they have to do, then wait.

## How work is tracked

All work is tracked in **GitHub Issues** on `stevehetz/invokedb`, in priority order on the
GitHub Project board **InvokeDB** (project 1, https://github.com/users/stevehetz/projects/1,
e.g. `gh project item-list 1 --owner stevehetz`). There is no other task list;
`docs/HANDOFF.md` has project state and history, not tasks. `gh project` commands need the
`project` token scope (`gh auth refresh -s project`, which the user runs).

1. **Every change has an issue** (except docs-only changes, see Hard rules). Title in the
   imperative; body with context, scope and a "**Done when**" checklist. Labels: one type
   (`bug`, `enhancement`, `documentation`, `chore`, `security`), one or more `area:*`
   (`backend`, `frontend`, `deploy`, `ci`), and `you` when a person has to do it. New issues go on
   the board by themselves (the project's Auto-add workflow, filter `is:issue`).
2. **The board says what's next.** Status is `Todo` (top = next), `In Progress` or `Done`.
   When the user asks "what's next", give the top `Todo` item, and if it's labelled `you`,
   only its next step (exact clicks or command).
3. **Start:** set the item to `In Progress`, branch from an up-to-date `main` as
   `<issue>-<short-slug>` (e.g. `6-remove-stripe`).
4. **Stay in scope.** A bug or follow-up found on the way becomes a new issue, not part of
   this branch. Mention it in the PR.
5. **Finish:** run the checks for what changed (`verify-backend`; frontend build + lint +
   typecheck), prettier, commit, push, and `gh pr create` with `Closes #<issue>` in the body and how it
   was checked. CI and the Claude review run on it. Tick the "Done when" boxes that are done;
   say plainly which aren't.
6. **Merge:** `automerge.yml` merges a PR that qualifies (see Hard rules, "Auto-merge");
   otherwise the user does. Never merge yourself unless asked. The merge closes the issue and
   the board moves it to `Done`. Decisions and findings made along the way go in issue or PR comments; anything a
   future session needs goes in HANDOFF or this file.
7. **Clean up local branches.** GitHub deletes merged branches on the remote, but local ones
   pile up. When you're back on `main` after a PR merges (and at the start of a session),
   run `git fetch --prune`, then delete local branches whose PR is merged or closed with
   `git branch -d <branch>` (it refuses a branch with unmerged commits; never use `-D` without
   the user's OK). Check with `gh pr list --head <branch> --state all` first, and keep any
   branch with an open PR.

Issues opened by `repair.yml` (failed CI/CD) are bugs: label and add them to the board like any
other.

### The cloud agent

An issue can be handed to a cloud agent instead of a local session: the user labels it
`agent`. `.github/workflows/agent-queue.yml` starts `implement.yml` on one issue at a time
(board order if the `PROJECTS_TOKEN` secret is set, otherwise issue number). Claude then works
it in GitHub Actions by the steps above and opens a PR labelled `agent-pr`; CI, the review and
auto-merge take it from there. The next issue starts when that PR merges or is parked
(`needs-owner`, `hold`). Review changes are handled by `revise.yml` (below). If the agent
stops without a PR, or its PR is stuck (failed CI, 2 hours idle, review changes after the last
revision round), the item gets `agent-stuck`, the user is mentioned, and the queue
moves on to the next issue (but holds once two agent PRs are stuck, which usually means something
systemic is failing); the stuck issue isn't started again until its PR is dealt with or the label
is removed. Closing an agent PR
without merging also marks its issue `agent-stuck`; removing the label asks for a retry.

- Only issues the user opened and labelled are worked, and the agent sees the issue body and
  the user's comments only. It has no databases (CI's `smoke` job tests the PR), no secrets
  and no production access.
- Good for well-scoped issues with a clear "Done when". Keep for a local session: anything
  needing a decision (`you`), visual checks, or production.
- When writing an issue for the agent, put everything it needs in the body: it can't ask.
- Follow-ups it finds (out-of-scope bugs, `.github/` changes it can't make) become issues labelled
  `agent-found`, at most 3 per run, checked for duplicates and added to the board (#69). The workflow
  strips `agent`/`you`/`hold`; then **bugs** (`bug`, not `security`) get `agent` from the workflow
  and are queued straight away (#196). Everything else (features, security triage, decisions) waits
  for the user to add `agent` (the queue checks who added the label).
- It can't change `.github/workflows/`: the Claude GitHub App has no `workflows` permission, so
  GitHub refuses the push (#10, #67). Don't label such issues `agent`; do them in a local session.

**Review changes** (`.github/workflows/revise.yml`): when the review labels an agent PR or a
repair fix PR `review-changes`, Claude fixes each finding or replies in its thread saying why
not, and pushes (an empty commit if it only replied), which starts CI and a fresh review. The
review reads earlier threads and replies, so an answered point isn't raised again. At most two
rounds per PR, then `agent-stuck`. On the user's own PRs it runs only when the user adds
`agent-fix` or runs it by hand. **Dependabot PRs** get it automatically too, after
`review-changes` or a failed CI run: Claude fixes what the update breaks (config, code, a lockfile
CI's npm rejects) or declines it (a comment and `needs-owner`; the user closes it). It never sees
a Dependabot PR's body, which quotes upstream release notes (#89).

**Dependency updates** (`.github/workflows/deps-update.yml`, #103): on the 1st of each month an
agent updates every npm package and opens two PRs on `deps/*` branches, labelled `dependencies`:
minor and patch updates, and majors (one commit per group of packages that move together; a
major it can't make pass every check is dropped, listed with the reason, and retried next
month). It follows `docs/DEPENDENCY_PINS.md`, the owner's short list of packages that only move
by a rule (e.g. `@types/node` follows the Node runtime). The PRs get CI, the review, revise,
resolve and auto-merge like agent PRs, but don't hold the issue queue. Dependabot only opens
**security** PRs for npm (and updates the GitHub Actions); never use `@dependabot ignore`
comments.

**Security fixes** (`.github/workflows/security-fix.yml`, #104): every 3 hours (Actions has no
trigger for new alerts), Claude fixes open CodeQL alerts on a `security/codeql-<n>` branch, in a PR labelled `security` that says
"Fixes code scanning alert #N", handled like an agent PR without holding the queue; a false
positive is dismissed by the workflow with a reason and comment (listed in the run summary, #124),
and one needing a decision becomes an `agent-found` + `security` issue. Leaked secrets are
never automated: only the user can rotate a credential.

**Merge conflicts** (`.github/workflows/resolve.yml`): when an agent PR or a repair fix PR
conflicts with `main` (another PR changed the same files first, often a `package-lock.json`),
Claude merges `main` in, resolves the conflicts, runs the checks and pushes, which starts CI and
a fresh review. It runs after every merge to `main` and every 30 minutes. One attempt per PR per
`main` commit; if it can't resolve them, the PR gets `agent-stuck`. Dependabot PRs and the
monthly `deps/*` PRs are included (GitHub runs no PR workflows while a PR conflicts). On the user's own PRs it runs only with
`agent-fix`. Workflows where Claude pushes check out with
`persist-credentials: false`, so the push uses the Claude app's token: a push with the workflow
token starts no CI, and a dispatched CI run doesn't count toward a PR's required checks.

## Formatting

- One root prettier 3 (`.prettierrc.json`, `.prettierignore`): 4-space indent, single quotes,
  no trailing commas, `arrowParens: avoid`, print width 100 (80 in `horizon-fe`).
- **Formatting happens at commit time.** `.githooks/pre-commit` runs
  `scripts/format-staged.mjs`, which formats staged files and stages them again. `npm install`
  turns it on through the `prepare` script, which sets `core.hooksPath`. Editors format on save.
- Don't reformat by hand while editing. When you finish a task, run
  `node_modules/.bin/prettier --write <files you changed>` (from the repo root) so the diff the
  user reviews is already formatted. If prettier reports a syntax error, the file doesn't parse.
- Always use the **root** prettier (the packages don't install their own).
- The backend email `.html` templates are intentionally not formatted.

## Backend conventions (`packages/horizon-be`)

- Layout: `src/web/http/*` controllers → `src/application/*` services → `src/core/*` managers
  and entities. `src/core/mongodb/collections.ts` names the Mongo databases and collections.
  `src/env.ts` lists every env var the backend reads.
- Import alias `@app/*` → `src/*`.
- Code style is `snake_case` for variables, methods and DB columns. Match the code around you.
- **TypeORM 1.x:** use `findOneBy`/`findBy`/`countBy`, `In(...)`, and an injected `DataSource`
  (`getManager()` and the global `createQueryBuilder` are gone). `invalidWhereValuesBehavior`
  throws on `null`/`undefined` in where clauses, so check for missing input and **return
  early** instead of querying with it.
- Decimal columns need `@Column({ type: 'decimal' })`, or TypeORM `parseInt`s them.
- **Nest 12 is ESM-only**; the backend stays CommonJS and loads it through Node's
  `require(esm)` (Node 22.12+). Jest can't, so `jest-esm-transform.js` compiles
  `node_modules/@nestjs/*` to CommonJS for the unit tests.
- **Mongo** uses the native driver (no mongoose). There is one database per account,
  `horizon:acct_<id>`, with grid collections such as `dg:row:file_<fileId>:acct_<id>` and
  `dg:column:...`, plus `horizon:tracking`. Await bulk writes and skip empty batches.
- In local mode one process runs all four backend roles (`IS_HORIZON_BE`, `_PRC`, `_SB`, `_FS`).
- Migrations live in `src/database/migration/`. Never edit a migration that has already shipped.
  Add a new one (see the `db-migration` skill).
- **Account scoping:** in an internal route, get the caller's account with
  `session_account_id(req.user)` (`src/web/http/_auth/request-account.ts`), and in `/api/v1`
  with `api_key_account(req.user)`; never from the query or body.
  Check that any table/folder id in the path belongs to it (`FileDirectoryService.assert_owned`,
  `WebFileService.validate`). `req.user` is a `Session` for a login token and an `Account` for an
  API key; API keys are only for `/api/v1`.
- Table templates (#142) are JSON files in `src/core/table-template/templates/` (one per
  template, checked by `table-template.spec.ts`); `tsconfig.build.json` copies them into `dist/`.
- Per-table API docs (#139): `src/core/table-docs/` builds a table's endpoints, examples,
  snippets (curl, fetch, `invokedb` client, Python) and OpenAPI spec from its columns
  (`GET /web-file/:id/api-docs`, `/web-file/:id/openapi.json`, `/api/v1/openapi?table=`).
  `api-smoke.mjs` runs the curl, fetch and Python snippets, so a snippet change must still run.
- Richer queries (#141): `POST /api/v1/query` and `/count` take `{ filters, match, sort, fields,
limit, cursor, explain }`; `src/core/web-file/row-query.ts` checks the body against the table's
  columns and builds the Mongo find (cursor = keyset on the sort columns + `_id`). The page cap
  is the plan's `query_page` (#183). `/get` and `/search` are unchanged.
- Plans (#183, `docs/PRICING.md` 3.2): `src/core/plan/plans.ts` is the one constant with every
  cap of Free, Starter and Pro (tables, rows per account and per table, storage, columns, API
  calls a month and per second, query page, CSV size, URL sources and schedules, webhooks,
  forms, views, audit days, per-key limits, AI allowances); **nothing else hard-codes a plan
  limit**. Subscription ids map as FREE → Free, BASIC → Starter, PLUS/PREMIUM → Pro until Stripe
  (#129). `INTERNAL_EMAILS` (demo*, e2e, verified) and accounts an admin made internal
  (`account.internal`, #277) have no counted caps. `TrackingManager.plan()`
  gives an account's caps and enforces them (reservations against races; account rows summed
  from each table's metadata; storage from `dbStats` `dataSize`, cached 30 s; the API quota is an
  atomic `$inc` per UTC month in `tracking:api_month`, the rate limit an in-memory token bucket;
  the 80% and 100% quota emails, #274, are claimed once per month by an `alerts` array on that
  document, `core/plan/quota-alert.ts`, and sent off the call's path);
  `assert_room` covers webhooks, forms, views and URL sources. A refusal is 403 (413 for an
  upload, 429 for the quota/rate) with `code: 'plan_limit'`, `limit`, `cap`, `upgrade_url`
  (`AllExceptionFilter` passes them on); the frontend's `request.js` emits `plan_limit` on the
  bus and `components/plan-limit-notice` links to the usage. `GET /plans` is public (the pricing
  page is built from it); `GET /usage` (session only, `core/plan/usage.ts`) feeds the Account
  page's meters. Deleting rows or tables never locks anything (only a plan change would; the
  read-only state is below). `HORIZON_TEST_PLANS` (set only by `smoke-env.sh`, never in
  production) puts demo5, demo6 and demo7 on plans with tiny caps for `api-smoke.mjs`.
- Plan state and idle accounts (#184, `docs/PRICING.md` 3.4): `account.plan_state` is
  `active`, `grace` (failed payment, full access until `grace_ends_at`, 14 days, then Free) or
  `read_only` (over the plan's caps), apart from `locked` (neither touches the other). Pure
  rules in `core/plan/plan-state.ts`; `application/plan/plan-state.service.ts` works it out
  from `GET /usage`'s numbers, stores it, sweeps every account daily in the processor (not the
  `HORIZON_TEST_PLANS` ones) and is TrackingManager's refresher. Every write path calls
  `TrackingManager.check_not_read_only` (403 `plan_read_only` with `over`): it's in `add_table`,
  `add_rows`, `add_columns`, `create_columns`, `validate_row_count`, `WebFileService`'s
  create/update paths and uploads, view/form/webhook/URL-import creation and AI column settings
  and fills (the AI column processor waits while an account is read-only). A new write path
  must call it too. A read-only account's state is worked out again on each refused write and
  after deletes, so deleting down to the caps lifts it at once. Idle free accounts:
  `core/plan/idle.ts` (pure) and `application/plan/idle-account.service.ts` (hourly in the
  processor) send warnings at 5 months and a week before 6, then delete through
  `AccountDeletionService` (the account's Mongo DB, its tracking documents, its Postgres rows).
  Last sign-in is recorded by `SessionManager.create_session`, the last API call by
  `TrackingManager.update_req_count` (hourly). Paid, internal and soft-deleted accounts are
  never touched; without Mailgun (outside local mode) nobody is warned, so nobody is deleted.
  `PUT`/`DELETE /test-plan` (404 unless `HORIZON_TEST_PLANS` lists the caller) lets the smoke
  test move demo5 between plans.
- Onboarding checklist (#143): `src/core/onboarding/` (pure logic + a manager storing one
  `tracking:onboarding:acct_<id>` document in the tracking DB, no Postgres change),
  `GET /onboarding`, `PUT /onboarding/steps/:step`, `PUT /onboarding/dismiss` (session only).
  `OnboardingInterceptor` on `/api/v1` ticks "call the API" after a successful call with the key.
  The frontend's checklist is `components/onboarding`, on the Tables page. The same document
  holds the funnel's times (#169): `signed_up_at` (signup, `AuthService`), `email_verified_at`
  and `table_created_at` (first table, `FileDirectoryService.create`), recorded without ever
  failing the request. `onboarding-funnel.ts` (pure) builds the funnel and
  `src/cli/onboarding-funnel.ts` prints it (`npm run onboarding:funnel`, `docs/OPERATIONS.md`).
- Import from a URL (#144): `src/core/url-import/` has the pure rules (`url-import.ts`: allowed
  URLs, Google Sheet links → CSV export, private-address ranges, JSON → CSV, sync settings), the
  fetcher (`url-fetch.ts`: checks every address it connects to, redirects, 10 MB, 30 s) and the
  source store (`url-import.manager.ts`, one `tracking:url_source` collection in the tracking DB
  shared by all accounts, so always filter on `account_id`). Routes are `/url-import` (session
  only). The fetch runs in the job processor (`URL_IMPORT`, `URL_SYNC` jobs in
  `WebFilePrcService`, which also queues hourly/daily syncs); re-syncs go through
  `web-file/url-sync-processor.ts` (replace, or upsert on a key column; everything is checked
  before anything is written). The API and UI smoke tests import this repo's files from
  raw.githubusercontent.com, so they need internet.
- Webhooks on row changes (#140): `src/core/webhook/` has the pure rules (`webhook.ts`: allowed
  URLs, events, HMAC signature `InvokeDB-Signature: t=<unix>,v1=<hex of "<t>.<body>">`, retry
  delays, payload rows), the sender (`webhook-send.ts`: private addresses refused on the address

## Frontend conventions (`horizon-fe`)

- Vue 3, Options API. Components are often split into `index.vue` + `<name>.html` (template, via
  `<template src>`) + `<name>.js` + `.scss`. Keep that split when editing an existing component.
- **Two areas, one app.** The public site (marketing, login, signup, pricing: `src/view/`,
  `src/network/`) is served at `/`, and the signed-in app (`src/components/`, `src/core/`) at
  `/app`. They were separate apps until 2026-11, and their global stylesheets clash. So each
  area's shell (`src/view/site.vue`, `src/components/app.vue`) is lazy-loaded and imports its
  own CSS, scoped to a class on `<html>` that `router.js` sets (`site-area`, `app-area`):
  `view/site-area.scss` and `app-area.scss` load the unchanged `stylesheet.scss` files inside
  `:where(html.<area>)`, which adds no specificity (#130). Both can be on the page, so links
  between the areas use the router like any other. Logging out (and deleting the account) is
  still a full page load, on purpose: it drops the account's in-memory data and the websocket.
  New area-wide CSS goes in the area's `stylesheet.scss`; don't import global CSS anywhere else
  (the exceptions: `main.js` imports Font Awesome and the highlight.js theme, which only style
  their own classes, and Element Plus's default theme). Route pages are lazy-loaded in
  `router.js`; `vite.config.js` gives ag-grid, Element Plus and Vue their own chunks. The UI
  smoke test checks the scoping and that signing in doesn't reload the page.
- Built with **Vite 6** (`vite.config.js`, `index.html` at the package root). Use the npm
  scripts (`start`, `build`, `preview`, `lint`), which `env.sh` feeds the env. Static assets in
  templates are plain `src="@/assets/x.png"`. `lodash` is imported explicitly (no globals).
  There is no jQuery: use the DOM API. Lint is ESLint 10 with a flat config
  (`eslint.config.mjs`, `vue/flat/essential`).
- **Light and dark (#290).** Every colour in both areas' `stylesheet.scss` is a token,
  `var(--h-<name>)`, from `src/theme-tokens.scss` (one `$light` and one `$dark` value each;
  text tokens pass WCAG AA on the surfaces they're used on). Use a token, or add one to both
  maps, never a literal; literals are only for things that look the same in both themes (white
  on a coloured badge, code blocks). `core/theme.js` sets `<html data-theme="light|dark">` and
  Element Plus's `dark` class (its `dark/css-vars.css`, loaded in `main.js`): the app from the
  account's choice (account menu → Theme; `account.theme`, `PUT /account/theme`, and
  `localStorage` `invokedb:theme`), the site and the form page from the device, an embedded form
  light unless `?theme=dark`. `index.html`'s inline script does the same before first paint;
  keep the two in step. The grid's params (`grid-theme.js`) and the form page's own `--f-*`
  variables follow the same switch.
- **Element Plus.** `main.js` loads the default theme (`element-plus/dist/index.css`) for both
  areas, in the entry chunk so it comes before the areas' CSS (a theme in a shared lazy chunk
  once loaded after the app's styles in production and overrode its nav). The app's colours are
  only `:root` variables, so `src/element-theme.scss` overrides just those on
  `:root.app-area`. Don't import a theme anywhere else. The app's CSS restyles the inner
  elements Element UI used to have, so Element Plus's extra wrappers are flattened in
  `stylesheet.scss` (`.el-input__wrapper`, the `.el-dialog` padding). Horizontal `el-menu`s need
  `:ellipsis="false"` or they fold items into "…". Use `link` buttons, not `type="text"` (removed
  in Element Plus 3), and icon components from `@element-plus/icons-vue`, not `el-icon-*` classes.
- **ag-grid 36** (`ag-grid-vue3`). The grid API comes from `onGridReady`; there's no
  `columnApi` or `gridOptions.api`. Keep grid options, column defs and the API out of reactive
  data (`markRaw`, or set them in `created()` rather than `data()`). Custom header/filter
  components are registered in `h-data-grid`'s `components` and named in the col defs, and
  receive `params` as a prop. `h-data-grid.js` registers `AllCommunityModule` (features are
  modules since v33). The grid's theme (`h-data-grid/grid-theme.js`, Theming API) is
  `createTheme()`, the core CSS with no parts, and its params only switch off what would draw
  over `stylesheet.scss`, which styles the grid; there's no ag-grid CSS import.
  Its `.ag-header-viewport` is `overflow: visible` (for the header dropdown menus), so ag-grid
  can't scroll the header; `h-data-grid`'s `body_scrolled` moves it with the body instead.
- `this.$bus` / `@/core/bus` is a small emitter with the old `$on`/`$off`/`$emit` names. Remove
  your handler with `$off` in `beforeUnmount`. Prefer props, emits or the store for new code.
- Help and changelog (#219): the site's `/help/:topic` (`view/pages/help`; topics in
  `help-topics.js`, their text in `help.html`) is linked from the site's nav and the app's header.
  **When a feature changes, update its help topic.** `/changelog` reads `changelog.json`, written by
  `npm run changelog` (`scripts/changelog.mjs`: merged PRs labelled `enhancement` or closing an
  `enhancement` issue).

## Gotchas

- **Postgres.app permission dialog:** the first connection from a new client app needs a click.
  If the backend is started without a terminal, it fails after 60s with
  `failed to verify "trust" authentication`. Ask the user to start `npm run dev` in their own
  terminal if that happens.
- Run long-lived servers (`npm run dev`) in the background, never as a blocking foreground
  command.
- Stripe was removed (no routes, no SDK, no checkout page). The `subscription` and `stripe_env`
  tables and the account's `stripe_*` columns are still in the schema; a later migration can
  drop them.
- `npm run db:demo` starts its own backend to load the example tables (`examples/setup.mjs`),
  so `npm run dev` must be stopped first.
- Mailgun and Telegram are optional. Without keys, emails and support requests go to the
  backend log.
