How it's built

One server, and a pipeline of agents

InvokeDB runs on a single server with Docker Compose. Most of its code is written by Claude in GitHub Actions: an issue goes in, and a reviewed, tested and deployed change comes out, with the owner deciding what gets worked and what needs a person.

Architecture

Everything runs on one DigitalOcean droplet (2 vCPUs, 4 GB) with docker compose. Only Caddy publishes ports; the cloud firewall lets in HTTP and HTTPS from anywhere and SSH only from the owner's address, plus a deploy's runner for the length of the deploy.

  • Backups: every night a script dumps Postgres and Mongo, encrypts them and uploads them off the server, keeping 30 days; a verify command restores the latest into throwaway containers and compares the counts. DigitalOcean's weekly droplet backup is a second copy.
  • Monitoring: UptimeRobot checks the site and the API every 5 minutes; Healthchecks.io expects each night's backup; errors from the API, the processor and the browser are grouped and stored on the server itself, with a Telegram message for each new one; the status page shows the server's own checks.
  • Deploys: the images are built on the server from the commit being deployed, and migrations run before the containers restart. The server's settings live outside the app folder, so a deploy ships code only.

The stack

Backend
NestJS 12 in TypeScript, with TypeORM on Postgres and the native MongoDB driver (no ODM). Each account's rows live in its own Mongo database, so tables can have any columns and one account's data never shares a collection with another's.
Frontend
Vue 3 and Vite 6, with ag-grid 36 for the spreadsheet and Element Plus for the controls. The public site and the app are one build with two areas, each with its own stylesheet; light and dark themes come from one set of colour tokens. Kanban, calendar, chart and map views are drawn in SVG, with no chart or map library.
API
A REST API for every table, with its own docs, snippets and OpenAPI spec built from its columns, and keys scoped to read or write and to some tables.
MCP server
/mcp lets AI agents list, query and change tables with an API key. It's written without an MCP SDK: a small JSON-RPC handler over stateless streamable HTTP, and each tool goes through the same paths as the REST API (quotas, locks, webhooks, the audit log). Connect an agent.
AI features
Ask AI, AI columns and cleanup call the Anthropic API, with a monthly allowance per account and a budget for the whole server. The model never writes code: edits are a fixed set of operations, checked and previewed before anything is saved.
Tests
Jest unit tests for the pure rules, an API smoke test that runs the built backend against real Postgres and Mongo on every PR, and a Playwright test of the main UI flows that runs against production.

The agent pipeline

Work is tracked only in GitHub issues. The owner writes an issue, puts it on the board and labels it for the agent; from there, GitHub Actions workflows take it to production. Claude runs in them through the Claude GitHub App.

Where a person stays in charge

  • The agent only works issues the owner opened and labelled, and sees only the issue and the owner's comments. Bugs it finds on the way become new issues instead of growing the change.
  • Every change reaches main through a pull request with CI passing. A PR that touches the deploy setup, the workflows or a migration is held for the owner.
  • The agent has no databases, no secrets and no production access, and can't change the workflows that run it.
  • A PR stuck on failed CI, idle for 2 hours, or out of review rounds is labelled and the owner mentioned; the queue moves on to the next issue, and stops if two are stuck.
